VISUAL SYSTEM REWORK AND LAUNCH STING (2026-10-14)

Screen-edge gap fixed (commit 3781044). Every element sat far from both the
left and the right edge; on the user's handset the gap measured ~300 px of a
2340 px landscape screen. Two defects, both in the shared screen base rather
than in any individual screen:
  1. HexScreen._apply_safe_padding() converted the device safe area with the
     wrong operation. DisplayServer.get_display_safe_area() reports PHYSICAL
     pixels while the layout works in LOGICAL UI units, so physical → logical
     means dividing by the window/viewport ratio. The code multiplied, so on a
     high-density handset a ~140 px cutout became a ~280 px inset. It was then
     mirrored onto both edges with no upper bound, hollowing the screen out
     symmetrically — which is why every element moved at once.
     Each edge now gets its own inset, correctly converted, capped at 6% of
     the width and 8% of the height. A cutout is physically bounded by the
     short edge of the panel, so the height cap is what keeps landscape
     phones honest (~86 px on a 1080 px tall screen).
  2. The full-bleed key art was scaled 1.0 → 1.035 → 1.0 forever (1.028 on the
     hub). Scaling a large texture by a fraction of a percent makes the pixel
     grid shimmer, which reads as a cheap wobble rather than as movement.
     Replaced with Atmosphere: drifting embers, a vignette and a slow light
     sweep drawn IN FRONT of the artwork. The art itself never moves. Ember
     positions snap to whole pixels and are driven by time, not accumulated
     randomness, so the effect is smooth rather than jittery.

UI redesign (commit 907f700). Expressed entirely through the data-driven
design system, so no screen had to change:
  - Palette: abyss base (#050a14) with three working hues — cyan informs,
    gold is the player's action, violet marks the epic and premium tiers.
    Everything else is a value step of the abyss. A narrow palette is what
    keeps a phone-sized screen legible. Signal red, verdigris and ember
    orange retuned for the new base.
  - Typography: refined scale (~1.2-1.35x between ranks), explicit tracking
    per rank (large type tightened so words read as shapes; small uppercase
    labels opened up so they do not clump), and a hard ink outline on
    headings, which sit directly on full-bleed artwork.
  - Surfaces: every raised surface casts a short crisp 4 px drop edge — the
    pixel-art depth idiom, square and resolution independent.
  - Google's four brand colours are deliberately left untouched.

  CORRECTION (commit 57b8c6e): that pass changed nothing the user could see,
  and the reason is worth recording. The two screens that exist use only
  EntranceDockPanel, GlassModalPanel, GlassNavButton, GlassButton and
  GlassPrimaryButton. Three of those five kept their colours as literals
  written into design.gd's own tables, below the palette block — so
  repainting the palette changed them by exactly nothing. The constants that
  did move feed the solid half of the system, which after the legacy sweep
  styles only settings_page. The literals are now replaced with GLASS_PANEL,
  GLASS_MODAL and GLASS_NAV, and no colour on a live surface is out of the
  palette's reach any more.
  Panels also get the drop edge that pass missed: the panel table builds its
  own styleboxes and was never routed through _apply_drop_edge. Panels on the
  canvas now share the crisp edge with buttons; the two glass panels that
  float over the artwork keep a soft lift, because a hard edge on those reads
  as a sticker.

Launch sting (commits 38fdb87, 57b8c6e, ef0ca36). SplashScreen is
run/main_scene: an explosion tears open the dark, HEXORA-STUDIO slams in as
pixel type, and PIXEL LEGENDS rises beneath it on a gentle upward arc.
Procedural rather than a video - a video adds a decode step and megabytes to
the APK, and it still could not replace the OS starting window. 5.0 s,
skippable by tap, then fades into the entrance screen.

Three defects are worth recording, because each was diagnosed from the spec
rather than from taste:

  1. The first version was poor and was rebuilt: wordmark and subtitle are
     centred as one block computed from their measured heights; the "smoke"
     was literally growing grey squares and is now a procedurally generated
     radial falloff drawn as layered puffs that cool and darken as they rise.

  2. The subtitle overlapped, three times over, every time it was positioned
     character by character - by summing isolated widths, by measuring
     running prefixes, and once on a fixed pitch with a 22% margin that the
     arithmetic said could not fail and the device did. The margin was never
     the problem; the premise was. Anything this project assumes about a
     font's metrics at run time is the thing that turns out to be wrong on a
     phone. Both lines are now baked from precomputed bitmaps whose advances
     were measured at build time, so nothing measures anything at run time.
     Baking is also what allows the arc and a per-letter colour ramp, both of
     which need per-letter placement.

  3. The 7x9 pixel face put one art pixel at roughly 27 device pixels across.
     Section 2 ("Visual Direction") and section 29 ("Final Visual Target")
     forbid exactly that by name: "Large chunky pixels", "Chunky pixel art",
     "The game must NOT look like Minecraft." The face was regenerated, not
     retuned - Chakra Petch Bold rasterised at a cap height of 92 art pixels
     with a hard two-level edge (no anti-aliasing, which would read as vector
     text), a 1 px outline, and a 3 px top highlight / bottom shade. One art
     pixel now lands at roughly 2.6 device pixels: ten times finer, with the
     wordmark keeping its footprint. tools/build_pixel_font.py regenerates
     it; the generated file says so rather than inviting hand-edits.

Effects (5.0 s): fire 280, smoke 110, sparks 80, embers 70, plus tumbling
pixel shards and twinkling four-point glints, two shockwave rings, a warm
bloom behind the type, and smoke tinted teal and violet rather than grey.
Fire cools through violet on a minority of particles so the burst is not one
flat orange.

The large app icon on black at first launch is Android 12+ drawing a starting
window with the launcher icon before the process has rendered anything. It is
OS behaviour, not the engine; Godot's own boot splash is already off
(boot_splash/show_image=false). Changing it needs an Android theme, and there
is no android/ directory in the project yet.

============================================================
1. PROJECT GOAL
============================================================

Build a fully 3D 5v5 mobile MOBA in Godot 4.4.

The gameplay structure, control philosophy, match flow, camera behavior, lane structure, combat loop, and overall player experience should belong to the same modern mobile-MOBA category as Mobile Legends, while all characters, abilities, maps, art assets, names, UI assets, effects, and other creative content must be original.

The game must NOT copy copyrighted characters, assets, names, maps, UI artwork, sounds, or other proprietary content from existing games.

Core target:
- 5v5 competitive MOBA
- Fully 3D world
- Mobile-first controls
- Dedicated authoritative game server
- Nakama backend
- Godot 4.4
- ENet / Godot MultiplayerAPI
- Server-authoritative simulation
- Client-side prediction and reconciliation where appropriate
- Modern mobile-quality rendering
- High-resolution refined pixel-art visual identity


============================================================
2. VISUAL DIRECTION
============================================================

The visual style must be:

- High-Resolution 3D Pixel Art
- Micro-Pixel Stylized Graphics
- Fine Pixel-Texture Aesthetic
- Crisp Pixel-Art Rendering
- Fine pixel clusters
- Sharp silhouettes
- Sharp texture details
- Stylized 3D characters
- Stylized 3D environment
- Modern stylized lighting
- High-quality materials
- Clean and readable VFX
- Premium mobile-game presentation

IMPORTANT:

The game must NOT look like Minecraft.

NOT:
- Voxel art
- Blocky Minecraft-style geometry
- Large chunky pixels
- Extremely low-resolution textures
- Primitive cube-based characters
- Full-screen extreme pixelation

Characters and environments must be fully 3D.

8. GAME SERVER
============================================================

Use a dedicated authoritative Godot headless server.

The server must:
- Run without graphical UI
- Run without client presentation systems
- Own the authoritative game state
- Validate player commands
- Simulate combat
- Simulate movement
- Simulate minions
- Simulate towers
- Simulate objectives
- Validate abilities
- Validate purchases
- Validate rewards
- Validate victory conditions
- Record match outcomes, and enough per-player data to audit a match after
  the fact

Recording is listed here, not deferred to a later phase, because it answers a
question no amount of validation can. Validation rejects what is invalid; it
cannot notice a player who uses legitimate commands in a way the designer did
not intend, because to the server that looks like ordinary play. Catching that
needs a record to look back at, and a record added after release has already
lost the matches that came before it.

Example launch:

godot --headless --match-id=1001 --port=9001

For MVP:
- One headless Godot process per match
- One match per dedicated process

This can later evolve into a more advanced server allocation system.

BEGINNER GLOSSARY
============================================================

The agent must explain these terms in simple language when they first appear.

CLIENT:
The player's game application running on the player's phone/PC.

SERVER:
The authoritative computer process that controls the real match state.

DEDICATED SERVER:
A server process running separately from a player's game.

HEADLESS:
A server running without graphics or a normal game window.

AUTHORITATIVE SERVER:
The server is the final authority over important game state.

RPC:
A way for one computer/process to request an action from another process.

TICK:
One simulation update performed by the game server.

SNAPSHOT:
A packet containing part of the current game state.

PREDICTION:
The client temporarily predicts its own movement before receiving the server result.

RECONCILIATION:
The client corrects its prediction when the authoritative server state arrives.

INTERPOLATION:
Smoothly displaying other players between received server states.

LATENCY:
The delay between sending and receiving data over a network.

NAKAMA:
The backend service used for authentication, accounts, matchmaking, social features, leaderboards, and related services.

OAUTH:
A standard system used to authenticate through an external identity provider such as Google.

TOKEN:
A temporary credential used to prove that a session or authentication step is valid.

ACCOUNT LINKING:
Connecting two login methods to the same player account, such as Guest + Google.

RESOURCE:
A Godot data asset used to store reusable configuration/data.

SCENE:
A Godot file containing a reusable collection of nodes.

NODE:
A basic building block inside a Godot scene.

NAVIGATION:
The system that helps characters find paths through the 3D world.

FOG OF WAR:
A system that hides information from players when their team should not be able to see it.
