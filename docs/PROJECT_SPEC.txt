============================================================
1. PROJECT GOAL
============================================================

Build a fully 3D 5v5 mobile MOBA in Godot 4.4.

The gameplay structure, control philosophy, match flow, camera behavior, lane structure, combat loop, and overall player experience should belong to the same modern mobile-MOBA category as Mobile Legends, while all characters, abilities, maps, art assets, names, UI assets, effects, and other creative content must be original.

The game must NOT copy copyrighted characters, assets, names, maps, UI artwork, sounds, or other proprietary content from existing games.

Core target:
- 5v5 competitive MOBA
- Fully 3D world
- Mobile-first controls
- Dedicated authoritative game server
- Nakama backend
- Godot 4.4
- ENet / Godot MultiplayerAPI
- Server-authoritative simulation
- Client-side prediction and reconciliation where appropriate
- Modern mobile-quality rendering
- High-resolution refined pixel-art visual identity


============================================================
2. VISUAL DIRECTION
============================================================

The visual style must be:

- High-Resolution 3D Pixel Art
- Micro-Pixel Stylized Graphics
- Fine Pixel-Texture Aesthetic
- Crisp Pixel-Art Rendering
- Fine pixel clusters
- Sharp silhouettes
- Sharp texture details
- Stylized 3D characters
- Stylized 3D environment
- Modern stylized lighting
- High-quality materials
- Clean and readable VFX
- Premium mobile-game presentation

IMPORTANT:

The game must NOT look like Minecraft.

NOT:
- Voxel art
- Blocky Minecraft-style geometry
- Large chunky pixels
- Extremely low-resolution textures
- Primitive cube-based characters
- Full-screen extreme pixelation

Characters and environments must be fully 3D.

The pixel aesthetic should mainly appear through:
- Texture design
- Fine pixel clusters
- Material details
- Color grouping
- Edge treatment
- Stylized shading
- VFX
- UI
- Icons
- Small visual details

Do NOT render the entire game at an extremely low internal resolution just to create a pixel effect.

Use native/high-resolution rendering with a refined pixel-art-inspired material and texture style.

Suggested texture resolution depending on asset importance:
- 256x256
- 512x512
- 1024x1024

Use higher resolutions for important hero textures and major environment assets when needed.


============================================================
3. CAMERA
============================================================

Use a 3D angled top-down MOBA camera.

Technical description:

- 3D Angled Top-Down Camera
- 3/4 Perspective
- Elevated Diagonal Perspective
- Perspective Projection
- Hero-Centered Camera
- Mobile MOBA-style camera

Do NOT call it "true isometric" unless orthographic projection is actually being used.

Camera must support:
- Configurable height
- Configurable distance
- Configurable pitch
- Configurable FOV
- Follow speed
- Smooth camera movement
- Zoom limits
- Map/world boundaries
- Hero-centered tracking

The camera should provide the familiar elevated diagonal gameplay readability expected from a modern mobile MOBA.

5. AUTHENTICATION & ACCOUNT SYSTEM
============================================================

Authentication must be designed from the beginning of the project.

Required authentication methods:

1. Google / Gmail Sign-In
2. Guest Login

Google authentication must use OAuth and be integrated with Nakama.

Players must be able to:
- Sign in with Google
- Continue as a Guest
- Link a Guest account to a Google account
- Preserve existing progress when linking
- Restore their account after reinstalling the game
- Restore their session when possible
- Log out
- Sign in with another account
- Reconnect to an existing game session when supported

Authentication, session management, token validation, account linking, and identity management must be handled by the backend/Nakama layer.

The dedicated Godot game server must NOT directly manage Google OAuth.

============================================================
8. GAME SERVER
============================================================

Use a dedicated authoritative Godot headless server.

The server must:
- Run without graphical UI
- Run without client presentation systems
- Own the authoritative game state
- Validate player commands
- Simulate combat
- Simulate movement
- Simulate minions
- Simulate towers
- Simulate objectives
- Validate abilities
- Validate purchases
- Validate rewards
- Validate victory conditions

Example launch:

godot --headless --match-id=1001 --port=9001

For MVP:
- One headless Godot process per match
- One match per dedicated process

This can later evolve into a more advanced server allocation system.


============================================================
9. NETWORKING
============================================================

Use:
- ENet
- Godot MultiplayerAPI

Target simulation tick:
- Approximately 30 Hz initially
- Make tick rate configurable
- Evaluate 60 Hz later if necessary

Client should send INPUT/COMMAND data rather than authoritative world state.

Examples:
- Move direction
- Stop
- Face direction
- Basic attack request
- Ability cast request
- Target selection
- Recall request
- Item purchase request

The server validates the command before applying it.


============================================================
10. RELIABLE VS UNRELIABLE NETWORKING
============================================================

Use unreliable ordered communication for:
- Frequent movement input
- Facing direction
- High-frequency transient input

Use reliable communication for:
- Important gameplay events
- Match state transitions
- Purchase confirmations
- Ability confirmations where required
- Death/respawn events
- Objective events
- Match result
- Authentication/session-related important messages

Important:

Reliable does NOT mean trusted.

The server remains authoritative regardless of network delivery mode.


============================================================
11. CLIENT PREDICTION & RECONCILIATION
============================================================

Use client-side prediction where appropriate.

Prediction may be used for:
- Player movement
- Facing
- Basic navigation responsiveness

Server remains authoritative.

When the server sends authoritative state:
- Compare predicted state
- Reconcile if necessary
- Correct client state smoothly

For other players:
- Use interpolation
- Do not directly snap between snapshots unless necessary

Do NOT allow the client to authoritatively decide:
- Damage
- Kills
- Gold
- XP
- Cooldown completion
- Item purchases
- Ability hit results
- Tower damage
- Objective ownership
- Victory
- Teleportation
- Impossible movement


============================================================
12. SNAPSHOT SYSTEM
============================================================

Design the snapshot protocol early.

Server periodically sends relevant world-state snapshots.

Snapshots may contain:
- Entity IDs
- Positions
- Rotations
- Movement state
- Health
- Mana
- Animation state
- Team
- Hero state
- Relevant combat state
- Objective state

Optimize snapshots so clients receive only relevant information.

Future optimization may include:
- Delta compression
- Interest management
- Entity prioritization
- Reduced update frequency for distant entities

============================================================
DEFINITION OF DONE / PHASE GATES
============================================================

The phase names and numbers in section 26 are the canonical development
sequence. Use these gates to verify that sequence; do not treat this list as a
second, differently numbered roadmap. A phase passes only when its listed
criteria have been implemented and tested.

PHASE 0 — FOUNDATION PASSES WHEN:
- The Godot 4.4 project imports, opens, and runs its basic scene without
  critical errors.
- Client, server, and shared responsibilities have clear boundaries.
- Shared data/build configuration and the basic networking bootstrap exist.
- A Godot headless server process can start without client presentation.

PHASE 1 — AUTHENTICATION & BACKEND FOUNDATION PASSES WHEN:
- Nakama guest authentication works, and Google authentication works when
  configured through a supported integration.
- Sessions can be created, validated, restored, and logged out safely.
- Guest-to-Google account linking preserves the existing player account.
- Authentication/session responsibilities are separate from match simulation.

PHASE 2 — TWO-PLAYER MOVEMENT PASSES WHEN:
- Two authenticated clients can join one dedicated test match and exchange
  the required messages.
- Server-authoritative movement and state synchronization work.
- Prediction/reconciliation and interpolation are tested where appropriate.
- The snapshot system carries the required state for the two-player test.

PHASE 3 — COMBAT PASSES WHEN:
- Basic attack, health, damage, mana, cooldown, and ability behavior work.
- The server validates combat outcomes; death and respawn work correctly.

PHASE 4 — MOBA CORE PASSES WHEN:
- Basic minion/lane/tower foundations, gold/XP/levels, base, and victory
  conditions work under server authority.

PHASE 5 — 5V5 PASSES WHEN:
- Ten players can be assigned to two teams with correct hero assignment,
  spawning, respawning, match timer, and team state.
- Core 5v5 networking is stable enough for continued development.

PHASE 6 — FULL MOBA MAP PASSES WHEN:
- The three-lane map, jungle, river, bushes/vision, bases, towers, objectives,
  paths, and navigation work and are testable in a match.

PHASE 7 — HEROES & ITEMS PASSES WHEN:
- Multiple heroes, roles, abilities, stats, and items can be selected and
  tested using data-driven definitions.
- The item shop and balance data work without hardcoding balance throughout
  simulation code.

PHASE 8 — PRODUCTION BACKEND PASSES WHEN:
- Required matchmaking, lobby/social/ranking, reconnect, and backend services
  are functional.
- Dedicated-server allocation, monitoring, and logging are tested for the
  chosen deployment model.
- Security, load, recovery, and production-operability requirements are met.


============================================================
BEGINNER GLOSSARY
============================================================

The agent must explain these terms in simple language when they first appear.

CLIENT:
The player's game application running on the player's phone/PC.

SERVER:
The authoritative computer process that controls the real match state.

DEDICATED SERVER:
A server process running separately from a player's game.

HEADLESS:
A server running without graphics or a normal game window.

AUTHORITATIVE SERVER:
The server is the final authority over important game state.

RPC:
A way for one computer/process to request an action from another process.

TICK:
One simulation update performed by the game server.

SNAPSHOT:
A packet containing part of the current game state.

PREDICTION:
The client temporarily predicts its own movement before receiving the server result.

RECONCILIATION:
The client corrects its prediction when the authoritative server state arrives.

INTERPOLATION:
Smoothly displaying other players between received server states.

LATENCY:
The delay between sending and receiving data over a network.

NAKAMA:
The backend service used for authentication, accounts, matchmaking, social features, leaderboards, and related services.

OAUTH:
A standard system used to authenticate through an external identity provider such as Google.

TOKEN:
A temporary credential used to prove that a session or authentication step is valid.

ACCOUNT LINKING:
Connecting two login methods to the same player account, such as Guest + Google.

RESOURCE:
A Godot data asset used to store reusable configuration/data.

SCENE:
A Godot file containing a reusable collection of nodes.

NODE:
A basic building block inside a Godot scene.

NAVIGATION:
The system that helps characters find paths through the 3D world.

FOG OF WAR:
A system that hides information from players when their team should not be able to see it.


============================================================
AGENT COMMUNICATION RULES FOR A COMPLETE BEGINNER
============================================================

When giving instructions, use simple language.

Prefer:

"Open this file:
res://client/authentication/guest_login/guest_login.gd

Replace its contents with the following code..."

Then explain what the code does.

Avoid unexplained instructions such as:

"Implement the auth service and wire the RPC."

If a technical term is necessary, explain it immediately.

When multiple files are required, present them in this order:

1. File path
2. Purpose
3. Complete code
4. Where to create it
5. What to change in Godot
6. How to run
7. How to test
8. Expected result
9. Common errors

The agent must not assume that the developer knows where a Godot file or setting is located.


============================================================
ORIGINAL CREATIVE DIRECTION MUST NOT BE LOST
============================================================

All existing Pixel Legends requirements remain mandatory.

The game must remain:

- Fully 3D
- 5v5 mobile MOBA
- 3/4 perspective
- Elevated diagonal perspective
- Perspective projection
- Hero-centered camera
- High-resolution
- Fine micro-pixel aesthetic
- Modern stylized lighting
- Crisp silhouettes
- Detailed materials
- Clean VFX
- Original creative identity

The game must NOT become:

- Minecraft-like
- Voxel-based
- Cube-character based
- Chunky pixel art
- Extremely low-resolution
- Full-screen low-resolution pixelated
- A copy of another game's characters, maps, names, artwork, or assets

All original architecture and gameplay requirements in this specification remain active.


============================================================
29. FINAL VISUAL TARGET
============================================================

"A high-quality fully 3D mobile MOBA with a 3/4 angled top-down perspective and modern mobile-MOBA gameplay structure, combined with a refined high-resolution micro-pixel art aesthetic.

The game must NOT look voxel-based or Minecraft-like.

Characters and environments are fully 3D, with extremely fine pixel-textured materials, crisp silhouettes, sharp details, stylized lighting, subtle pixel clusters, modern mobile-quality rendering, clean VFX, and strong gameplay readability.

The pixel aesthetic should be visible in the art direction, textures, shading, UI, VFX, and material details without making the entire image look low-resolution or heavily pixelated.

Authentication must support Google/Gmail login and Guest login through Nakama, including account linking and session restoration.

The final result should feel like a polished competitive mobile 5v5 MOBA with an original high-resolution pixel-art identity."
